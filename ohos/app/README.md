# DSH HarmonyOS App · Local Validation Project

English | [中文](README.zh.md)

This is an oheco community wrapper for local testing, not an official client and not a published release. It is deliberately thin: the service runs in a terminal, and the app only reads the address the service announces and opens it in the built-in WebView. See [VALIDATION.md](VALIDATION.md) for acceptance status.

The display name is `Deepseek Harness`; the bundle name is `org.oheco.deepseekharness`, whose third segment is the catalog package name `deepseek-harness` with its hyphen removed. Icons follow the HarmonyOS **layered icon** specification (generated by `ohos/sync-app-logo.py`): `AppScope/resources/base/media/` holds `background.png` (1024×1024 solid tile), `foreground.png` (1024×1024 transparent mark only) and `layered_image.json`, whose `layered-image` object names both layers. `app.json5` and `abilities[].icon` both reference `$media:layered_image`, and **the system draws the rounded tile** — cutting rounded corners into the bitmap yourself is an explicit review failure, so no layer carries rounding. The start window uses a transparent `ability_icon.png` from the module, with a white-mark variant under `resources/dark/media/` for a dark theme. `app_icon.png` remains as a flat, pre-rounded fallback for any surface that cannot compose the layered icon.

The launcher entry and the window decoration read the same ability icon on this device, so the desktop and title-bar icons cannot be set independently: both show the composed layered icon. After changing the bundle name, generate or select a signing profile for that exact name in DevEco; data from the old bundle is not migrated automatically.

This project carries the completed App's tracked sources from `deepseek-harness-0.1.7`, including search, context-menu, external-link, path, theme and log interactions. The local App version is `0.2.0-rc.2-ohos.1 / 1000002`; the bundle ID is unchanged, so a later manual installation upgrades the same App rather than installing alongside it. The independent unsigned export is `export/DSHApp-0.2.0`; old projects and their signing configuration remain read-only. Old checks or signed HAPs are not evidence for this version. See [VALIDATION.md](VALIDATION.md) for checks actually run.

## 1. Open in DevEco

1. Open this directory, which contains `build-profile.json5`, rather than opening only `entry`.
2. Prepare DevEco/HarmonyOS SDK and ArkTS toolchains that support the declared SDK. The default target is ARM64 HarmonyOS PC / 2in1; compileSdkVersion, targetSdkVersion, and compatibleSdkVersion are all `6.1.0(23)`.
3. Configure **App signing** with your own developer account. The project contains no certificates, private keys, profiles, or personal `local.properties`. Ordinary development signing does not confer system-app status.
4. Sync the project, then Build/Run `entry`.

The project declares only `ohos.permission.INTERNET` plus the normal-level, user-granted `ohos.permission.READ_WRITE_DOCUMENTS_DIRECTORY`. It requests no system-level permission and changes no device policy.

`entry/src/main/cpp` remains in the project: it is the process supervisor from the earlier in-app launch attempt. The two-step flow does not use it, but it is kept so devices that do hold shared-directory access can keep experimenting, which is why the CMake reference in `entry/build-profile.json5` is unchanged.

## 2. Why two steps

A device run proved that an ordinary signed app **cannot read the shared runtime** (`open` returns `EPERM`), **cannot execute an ELF from its private directory** (`errno=13`), and has no system Node (`/system/bin/node` and friends are absent). So it can neither run the oo-installed Node nor ship its own runtime inside the HAP and execute it. The two-step flow hands startup to the terminal and keeps the app to presentation only.

## 3. How it works

The home page has exactly two blocks:

1. **One command**, copied and run in a HarmonyOS terminal:

   ```sh
   zsh /storage/Users/currentUser/dev/ohos/harness-ohos-0.2.0-local/run-web.zsh > /storage/Users/currentUser/Documents/dsh-0.2.0-run.log 2>&1 &
   ```

   The command explicitly selects the independent 0.2.0 local package, never an older `dsh` on PATH. Its default port is OS-selected and its state is separate from existing settings, sessions and credentials. The log goes to Documents under the shared home; the app reads it through the normal-level Documents permission and falls back to the **Select the log file** picker when the direct path is refused. The displayed command and log name come from `RuntimeDefaults.ets`: `ohos/package-app-project.py` generates this same local entry by default. After moving the runtime, regenerate a new export with `--web-launcher <path>` and, if necessary, `--home <shared-home>`. The launcher accepts explicit `DSH_020_HOME` and `DSH_020_PORT` overrides for isolated tests; inherited generic `DSH_HOME` does not select an old state directory. Do not repeat the startup command while this instance is already running.

2. **A persistent waiting indicator.** The app reads that log once per second and takes the readiness address from it; **before opening anything it connects once**: only an address that actually answers switches the page to the WebView. A log left behind by an earlier run therefore cannot open a dead page. A new port (restarted service) is re-checked and reloaded.

Once open, the WebView occupies the whole window: no title row, no back button and no settings entry. The system Back key handles web history first.

The theme follows the system, which needs one extra step: ArkUI does not re-render a page when the system colour mode changes, so the system-drawn title bar switched while the page kept its old colours. `EntryAbility` therefore republishes the current colorMode into AppStorage from `onConfigurationUpdate`, and the page binds it with `@StorageProp`, so a theme change re-renders the page and re-resolves its `$r()` colours; startup also states the follow-system choice explicitly. Both palettes live in `entry/src/main/resources/{base,dark}/element/color.json`.

Opening the WebView also flashed white once: ArkWeb paints a default empty surface before the page content, independent of the theme. The Web component therefore carries the themed background, and a same-theme cover hides it until `onFirstScreenPaint` (the first content paint) or `onPageEnd`, whichever arrives first.

The page only talks to local `127.0.0.1`, but ArkWeb reports `navigator.onLine` as false while a fresh WebView is still resolving system network state. The Harness client reads that flag at boot and parks in its disconnected state until its own reconnect control is used. The app therefore injects a small script before the document starts, so the page sees the local connection it actually uses, and a transient system offline event cannot park it.

The log lives in `~/Documents/dsh-0.2.0-run.log`, not under the dsh state directory: this app runs in its own sandbox and cannot assume read access to the terminal's dsh data, whose location also depends on that process's environment. Even in Documents, files are `-rw-rw----` (owner plus the `file_manager` group), which this app does not join, so it requests the normal-level `ohos.permission.READ_WRITE_DOCUMENTS_DIRECTORY`; if the direct path is still refused, the waiting block shows a **Select the log file** button that grants read access through the system file picker, which needs no special permission.

Address rules: a **newline-terminated** complete line, an explicit `http://127.0.0.1:<port>` or `http://[::1]:<port>` authority, a nonzero port and a nonempty token; a line carrying the upstream LAN suffix is accepted, but only the loopback address is opened. The address reaches the WebView in memory only and is never written to preferences or log files.

### Desktop interactions

Ctrl+F opens a page-search bar with match counts; Enter / Shift+Enter move between matches and Esc closes it. Search covers loaded page content, not unloaded session history. Gesture zoom is disabled; external navigation is handed to the system.

Right-click offers copy and actions for HTTP(S) URLs or `~/` and `/storage/Users/currentUser/` paths. Selected text takes precedence; otherwise the wrapper checks a real link or bounded DOM text at the pointer, including adjacent syntax-highlighting spans and quoted paths with spaces. Blank pixels, passwords, canvas text and iframe text are not inferred. Empty results show no menu or message; paths containing three or more consecutive dots or an ellipsis are not actionable. Native overlays use the page's light/dark DSH colors, with left-aligned menu rows. Search starts at the top right and its background can be dragged within the window.

Path menus offer copy and **Show in file manager** only. A directory opens directly; a file opens its parent directory through Huawei's file-manager launch interface, without guaranteed file selection. The wrapper does not open editors, read file contents, request per-file authorization or create copies. Symlinks and paths outside the user home are refused. Errors use a bottom toast that disappears after three seconds, not a persistent overlay.

## 4. Known limitations

- The user must run one command in a terminal; the app cannot start the service itself, which is a platform-permission outcome.
- The address carries a local session token. The log stays on your own device and the app does not copy it elsewhere; you can delete the log once you are done.
- The Web interface is served by the independent local runtime, not bundled into the HAP. That runtime must be prepared before using the home command or running the Web integration test.
- The app is not resident and does not stop the terminal service. A previously loaded page may show its own disconnected state after the service stops; a new readiness address is checked before loading.

## Local source checks

Run these from the Harness source repository root, not from the exported project alone:

```sh
python3 -B ohos/test-app-project.py
node --test ohos/app/tests/*.test.mjs
python3 -B ohos/sync-app-logo.py --check
# Only after preparing the independent runtime:
python3 -B ohos/test-app-web.py
```

The logic tests need TypeScript from the checkout's locked Node dependencies; `NODE_PATH` may explicitly select a read-only older compiler installation when new dependencies are not ready. The Web test uses a new shared home/log and `DSH_020_HOME` under `$TMPDIR`, then stops its own process group and cleans those directories. `check-app-arkts.cjs --sdk <installed-ets-sdk> --output <new-directory-under-TMPDIR>` performs the available standalone semantic check, not a complete DevEco build. The retained native supervisor is unchanged and unused by the two-step page; its earlier results are not this version's evidence.

To create another unsigned export without running a package-manager check, use `python3 -B ohos/package-app-project.py --output <new-archive-directory-under-TMPDIR> --export-project <new-export-directory>`. It refuses existing export directories and never reads old personal signing files. Temporary archive/check directories must be cleaned after collecting results. No HAP build, signing or installation is performed by these commands.
